## 一、查新目的与创新点

### 1.1 查新目的

回答两个问题：

1. 本项目"AI Agent 高风险操作审批 + 终端接管 + 防篡改审计链"的组合，是否已有完全相同的公开实现？
2. 本项目"一份资源描述同时驱动 MCP 工具、Guard 权限与 MHS/MCP/A2A 协议绑定"的模型，是否已有完全相同的公开实现？

### 1.2 拟查新创新点（收窄为两条）

**创新点 A（主）**：一种在 AI Agent 操作本地终端或硬件时，由用户通过 Web 界面实时审批高风险操作、可在同一界面接管终端，并把审批决策与执行结果写入同一条防篡改审计链的机制。

**创新点 B（辅）**：一种资源描述模型（UniSpec v0.4），用同一份描述同时生成 MCP 工具定义、Guard 权限规则与协议绑定字段（`hardware_side` / `agent_access` / `inter_agent`），设备以 retain 自描述即可被零配置发现。

> 说明：不把"协议统一平台"作为查新点。统一描述、工具集成、工作流编排均有大量公开工作，
> 绝对首创不成立；本报告只主张上述两个**组合层面**的具体机制。

## 三、与研究报告创新点的对应关系（映射说明）

**查新点 1 对应研究报告创新一**（一份描述同时驱动工具、权限与协议位置）：

- 检索重心：设备自描述 / MCP 工具映射 / 协议绑定字段组合；
- 对比对象：W3C WoT、MCP 官方 `tools/list`、MCPAggregator、IoT-MCP；
- 结论表述："WoT 与 MCP 分别提出了物描述与工具描述；UniSpec v0.4 把协议绑定、控制机制
  与工具/权限规则收敛到同一份描述——该字段组合与工程实现在公开检索范围内未见完全相同实现。"

**查新点 2 对应研究报告创新二与创新三的组合**：

- 单独"审批"或"终端接管"均有公开实现（Dify/Coze 工作流审批、LangGraph/OpenAI Agents SDK
  工具审批、terminal-mcp/tlive 端子接管），**不主张单点首创**；
- 本次主张的是组合：工具级审批策略绑定统一资源描述 + 审批/执行共享 trace 写入防篡改哈希链
  + 同一 Web 控制台联动终端接管与瀑布图；
- 结论表述："未见与本作品完全相同的报道；新颖性在于组合——审批 + 终端接管 +
  审计链联动在同一事件流中的工程实现。"

## 五、逐条比对

### 5.1 创新点 A：审批 + 终端接管 + 防篡改审计链

**单独要素均已有公开实现：**

- 工作流/工具审批：Dify Human Input、Coze 中断恢复、LangGraph interrupt、OpenAI Agents SDK `needsApproval`、AutoGen `human_input_mode`。
- 终端接管：terminal-mcp 的"点击接管、Agent 写入暂停"；tlive 的远程审批 + 接管输入。
- 防篡改审计：Agent Flight Recorder 的哈希链/Merkle、TrustNotch 的 SHA-256 链 + 外部锚定、IETF NHE 审计链草案。

**组合层面的差异：**

1. 本项目的审批策略绑定在 **UniSpec 工具权限**上（能力级 `permissionLevel` + `readOnly`），不是只绑在工作流节点或对话轮次上；同一套策略同时覆盖 MCP 工具与 MQTT 硬件写操作（`control_pump`）。
2. 审批决策（批准/拒绝/改参/超时）与随后的工具执行结果写入**同一条审计哈希链**，并共享 `trace_id`；可在 `/api/audit/verify` 事后逐条校验。
3. 终端接管与审批卡片位于**同一个 Web 控制台、同一条事件流**：审批时瀑布图显示 `guardrail.approval` 等待态，批准后终端显示实际下发的设备命令（`terminal.command` 事件）。
4. 公开资料中 terminal-mcp / tlive 已经覆盖"审批 + 接管"；因此本项目**不主张"审批 + 接管"本身首创**，只主张"审批策略绑定统一资源描述 + 决策与执行共享 trace 写入哈希链"这一组合在公开检索范围内未见完全相同的开源实现。

**结论表述（建议）**：

> "公开资料显示，工作流审批、终端接管、Agent 审计链分别已有实现；本项目的具体组合——
> 以统一资源描述驱动工具级审批、在同一 Web 控制台联动终端接管、并将审批与执行写入
> 同一条可验证哈希链——在本次公开检索范围内未见完全相同的开源实现。属于组合创新/
> 工程集成创新，不主张单点首创。"

### 5.2 创新点 B：一份描述驱动工具、权限与协议绑定

**公开先例：**

- W3C WoT Thing Description 已提出"一份物描述统一描述设备能力"（概念层面）。
- MCP 的 `tools/list` 已用 `name` / `description` / `inputSchema` 描述工具。
- MCPAggregator 做服务端工具聚合；IoT-MCP 做 LLM 与 IoT 的桥接。

**差异：**

1. UniSpec v0.4.0 把 `protocol_bindings`（`hardware_side` / `agent_access` / `inter_agent`）与 `control_mechanisms`（`mcp_tool` / `cli` / `code_file`）写进同一份资源描述，并在 `tools/list` 的 `_meta.unispec` 中暴露。
2. 同一份描述同时生成 MCP 工具定义、Guard 校验规则与协议绑定，避免"工具描述一套、安全规则另一套"的配置漂移。
3. 设备以 retain 发布 UniSpec 即可被零配置发现（SIL 0.23s；真机 retain 注册已实测）。

**结论表述（建议）**：

> "WoT 与 MCP 分别提出了物描述与工具描述；本项目把协议绑定、控制机制与工具/权限规则
> 收敛到同一份 UniSpec v0.4 描述，并在设备自描述发现上完成 SIL/真机验证。该字段组合
> 与'一份描述驱动工具、权限、协议绑定'的工程实现，在公开检索范围内未见完全相同的开源实现。"

## 六、查新结论

1. **创新点 A**：单独要素（审批、终端接管、审计链）均有公开实现；"审批 + 终端接管"的组合也有 terminal-mcp / tlive 等公开项目。本项目的差异是**审批策略绑定统一资源描述、审批与执行共享 trace 写入哈希链、同一 Web 控制台联动**；建议以"组合创新"表述，避免"国内外未见"。
2. **创新点 B**：WoT/MCP 提供了概念先例；UniSpec v0.4 的**字段组合与一份描述驱动工具/权限/协议绑定**在公开检索范围内未见完全相同实现；建议以"工程集成创新"表述。
3. **总体结论**：本项目具备**组合层面的新颖性**，但不具备"基础要素首创"；在申报书中应明确"借鉴了哪些公开标准/产品，自己新增了哪一层组合与验证"，这比声称"全都没见过"更符合评审对科学性的期待。
