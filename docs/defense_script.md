## 三、逐页讲稿

### P1 封面（10s / 5min版：10s）

- 报题目、姓名、学校、指导教师。不展开，直接进痛点。

### P2 痛点：工具碎片化 + 安全缺失（35s / 5min版：30s）

- "接入 AI 工具今天有三个真实痛点：**第一，接入成本随工具数线性增长**——一个工具一百行代码，二十个就是两千行，全写在 Agent 侧；**第二，安全防护各写各的**——有的做了参数检查，有的直接字符串拼接执行命令，这正是命令注入的经典入口；**第三，能力描述没有统一标准**，Agent 没法自动理解一个工具能做什么。"
- 指右侧深色卡："这不是我猜的，是第三方披露的 MCP 生态安全现状：**30 多个 CVE、最高 CVSS 9.6；38% 的 MCP 服务器没有任何身份验证；装 10 个 MCP 插件被攻击概率 92%**。"
- **停顿一拍**，让评委看完三个数字再翻页。

### P3 核心思路：AI 世界的 USB-C（25s / 5min版：20s）

- "我的解法用 USB-C 来比喻：左边五类软件资源加上真实硬件，中间是 UniSpec 统一描述，右边 Agent 只看到一份 tools/list。"
- 关键句（放慢）：**"背后资源可以随便换，Agent 零改动——这就是统一接口的价值。"**

### P4 创新一 UniSpec：一份说明书说清一个资源（40s / 5min版：20s）

- "UniSpec 是我定义的能力描述规范，七个字段：id、type、name、protocol、endpoint、capabilities、constraints。核心是 **capabilities**——能做什么、参数 Schema、读写权限，都在这一段。"
- 指右侧："五类资源加真实硬件用同一套七要素。更重要的是**一份 UniSpec 生成三份产物**：给 Agent 的 MCP 工具定义、给安全层的校验规则、给人类用的 CLI 脚本——描述和安全不会漂移，因为它们同源。"

### P5 创新二 适配器：一套协议接入一切（40s / 5min版：20s）

- 指五张卡片："五类适配器实现同一套三方法协议 discover、list_tools、call_tool，核心层对资源类型完全无感。MQTT 做自动发现和写回执，CLI 用 shell=False 沙箱，REST 导入 OpenAPI，脚本走路径沙箱，数据库只读加受限写。"
- 指下排："22 个工具分**软件档 11 + 硬件档 8 + 温室模拟节点 3** 三档，**档位隔离**：硬件工具挂设备命名空间、独立限流配额，物理执行类能力一律 write 权限加回执确认加 600 秒时长上限——高频软件调用不会误触真实设备。"
- 收尾句："**新增一类资源等于新增一个适配器，核心层零改动。**"

### P6 创新三 工作流引擎（35s / 5min版：25s）

- "把『决定做什么』和『具体怎么做』分开：Agent 一次生成声明式蓝图，引擎来执行。"
- 指三步："演示场景 office_cooling：读室内温度 31 度，查室外天气，开空调降温——**一次调用 3.97 秒完成三步闭环**；条件表达式用我自研的安全解析器求值，**零 eval**。"
- 预告一句："同一套引擎，等会儿在温室模拟器上 1.30 秒完成浇水闭环。"

### P7 创新四 Guard：安全是必经关卡（45s / 5min版：35s）

- 指管道："所有调用必经六道关卡：存在性、权限、限流、参数校验与注入拦截、**Schema 验签**、审计。"
- 指大数字："**命令注入与越权调用的实测拦截率是 100%**。参数里带 `x; rm -rf /`，执行前就被 1007 拦下；用只读权限开空调被 1003 拒绝，但查空调状态正常放行——**能力级权限粒度**。"
- 指第三行："第一批改进我加了 **Schema 签名**：每个工具描述注册时算 SHA-256 哈希、用 Ed25519 签名，调用前验签——注册之后悄悄篡改工具描述的『工具投毒』攻击会被直接拒绝；审计记录还形成**哈希链**，篡改一条就能定位。"
- 关键句："**无论调用方是 LLM 还是脚本，Guard 一视同仁。**"

### P8 ESP32 温室灌溉闭环（模拟器）（60s / 5min版：45s）★ 核心亮点，放慢

- "前面都是软件验证，这一页是**温室灌溉节点**：用 Python MQTT **模拟器**复现真实 ESP32-S3 节点的传感器读数与水泵回执——土壤湿度、光照强度、以及水泵开关能力。"
- 指右侧三步："设备端只发布一份 UniSpec（retain 消息），平台**零配置**自动发现；土壤湿度掉到 **25%**，低于 30 的阈值，工作流条件满足——**自动开泵浇水，水泵回执确认**。"
- 指三个数字："一次 run_workflow 调用 **1.30 秒**完成完整闭环；水泵写回执端到端 **100 毫秒**，带 QoS1 确认和 600 秒时长上限；模拟器上线到出现在 tools/list 只要 **0.23 秒**。"
- 加一句对照："上一届我做『智慧生态系统』，每接一个传感器都要在平台逐个配置；这次设备发一份描述就能用——**这就是统一规范在异构节点接入上的价值**。"
- 诚实加分句："模拟器如实复现了协议细节：写回执按 request_id 精确匹配、浇水后土壤湿度回升、600 秒时长上限到点自动停泵；真机固件骨架已预留（`docs/hardware/firmware/esp32`），当前以模拟器为准、未烧录。"

### P9 通用性矩阵：4 类真实硬件 + 1 类模拟节点 × 6 类适配器（35s / 5min版：跳过）

- "为了证明『配置即接入』不是巧合，我做了 4 类真实硬件在环测试：USB 摄像头走脚本适配器、智能插座走 REST、手机当传感器节点走 MQTT、PC 自己走 CLI——加上 ESP32 温室模拟节点，**4 类真实硬件 + 1 类模拟节点、6 类适配器（5 类已实装、1 类已规划）、核心代码零改动**。"
- "其中 3 类是**纯配置**接入——YAML、OpenAPI 规格、App 配置，只有摄像头写了 30 行 Python；硬件总成本 80 到 130 块钱，低成本可复制。"

### P10 性能数据（25s / 5min版：20s）

- "三个关键数字：CLI 调用 **68 毫秒**、设备读取走状态缓存 **0 毫秒**、一次工作流调用三步闭环 **3.97 秒**。"

### P11 安全数据（30s / 5min版：25s）

## 四、高频问题库（赛前过一遍，答案口播级）

**Q1：为什么不用 MCP 官方 SDK，要自研 JSON-RPC 路由？后来又为什么迁移 FastMCP？**
> 分两段答：最初自研有三个原因——2026 年 7 月 MCP 转向无状态核心、我需要把 Guard 管道嵌在唯一入口上、协议行为完全可控。跑通后我做了重新评估：`server/discover` 能力广告和双协议时代协商属于"协议公共部分"，自己维护边际成本越来越高，于是把**协议层迁移到 FastMCP 4**，自研的路由、编排、安全插件全部保留，原自研网关降级为**回退路径**，迁移经过 139 项既有测试回归验证。结论：**值得自研的不是协议，是路由、编排与安全这些差异化层**。（dev_log §三；研究报告 4.4）

**Q2：你这个和 MCP 本身有什么区别？是不是套壳？**
> MCP 解决"Agent 怎么调用工具"的协议格式；我解决"**资源怎么统一变成安全工具**"。MCP 不规定能力怎么描述、安全谁来做——这些恰恰是生态里 38% 服务器无鉴权的原因。我的平台是 MCP 的**生产者侧**：任何资源注册进来，自动变成一个带安全管道的 MCP 工具。类比：MCP 是 USB-C 的针脚定义，我做的是那台"什么设备都能插的 Hub"。

**Q3：安全为什么放平台层，不放在 Agent 侧或靠模型自己判断？**
> 因为 AI 模型的输出是概率性的——它可能被提示注入，可能自己生成奇怪参数。把安全寄托在"模型不出错"上，等于把门锁交给客人。我的原则是**假设调用方会犯错**：Guard 嵌在网关唯一入口，模型再离谱的请求也过不了参数校验和权限检查。

**Q4：无状态具体是什么意思？**
> 无状态指网关不保存会话——每个请求自包含。好处一：水平扩展加机器就行，不用粘性会话；好处二：服务重启不丢能力，工具注册表落 SQLite，重启自动恢复 22 个工具（实测过）。MCP 2026-07 版自己也在往无状态转，FastMCP 4 按连接自动协商新旧协议版本，旧客户端也能接。

**Q5：ESP32 为什么用 MQTT 接入，不用 HTTP？**
> 三个理由：一，**retain 保留消息**让设备"发一份描述即注册"，网关晚启动也能立刻拿到；二，**QoS1 回执**给物理写操作（开泵）确认依据，HTTP 做不到断线补投；三，30 秒周期上报 + 状态缓存在网关侧，Agent 读数是 0ms，不用每次唤醒设备。弱网下回执超时我放宽到 3 秒并做了幂等重试，不会重复开泵。

**Q6：温室节点（模拟器）的代码量是多少？都是你写的吗？**
> 设备侧是 Python MQTT 模拟器，约两百行：传感器读数模拟、UniSpec 组包、命令订阅与 QoS1 回执、时长上限保护；**平台侧接入是 0 行**——设备发布 UniSpec 就被自动发现。真机固件骨架已预留（`docs/hardware/firmware/esp32`），当前以模拟器为准、未烧录。仓库每阶段都有设计文档和测试报告，12 个工程问题及解决过程在 dev_log。指导教师指导方向，代码和文档是我完成的。

**Q7：档位隔离具体怎么实现的？**
> 三层：命名空间——硬件工具挂在设备命名空间下（如 `iot.irrigation_01.control_pump`）；配额——硬件档独立限流 scope，软件档高频调用挤占不了设备配额；物理约束——执行类能力 write 权限 + QoS1 回执 + 600 秒时长上限。这样即使 Agent 失控刷调用，也只是刷不动，而不是让水泵停不下来。

**Q8：Schema 签名的私钥放哪里？会不会是伪安全？**
> 如实说：当前是演示环境，签名密钥本地生成、随平台部署，防的是"工具描述在注册后被悄悄篡改"这一攻击面——这正是 MCP 生态已披露的工具投毒缺口。生产环境应把密钥放进 KMS/HSM 并按服务器身份分发，我在报告里写明了这个边界。**关键是机制本身可用且经过拦截验证**（表 7 第 5 行）。

**Q9：为什么土壤阈值是 30、温度是 25？**
> 30% 是我这盆绿萝的浇水下限（电容式传感器实测干土约 22-28%），25°C 是多数室内绿植的活跃生长温度——两个条件同时满足才开泵，避免冬天低温浇水伤根。阈值写在 UniSpec 的 constraints 和工作流 condition 里，可按植物种类调整，不是硬编码。

**Q10：5×6 矩阵里 SQL 和 WebSocket 为什么是空的？**
> 如实说：SQL 适配器已在软件资源上验证（db_query/db_execute），硬件直连场景（时序库接传感器历史）在计划中；WebSocket 适配器是下一个要做的。矩阵上我把它们标成"待接入"，**不把规划画成已完成**。5 类已实装的覆盖已经足以支撑"配置即接入"的结论。

**Q11：工作流为什么不用 LangChain / LangGraph？**
> 两个原因：一，我的工作流是**声明式蓝图 + 平台执行**，Agent 只出一次意图，不需要框架在 Agent 侧逐步驱动——省 token 也更稳定；二，表达式求值我要求零 eval，自研 60 行的安全解析器比引入框架更可控。判断标准不是"库大不大"，而是哪个方案能审计。

**Q12：演示时模拟器/模型不稳定怎么办？**
> 每一环都有降级：模拟器失败则重启 `sim_esp32_greenhouse`，或改播预录片段 `03b_esp32_irrigation.mp4` 继续后续幕；LLM（加演环节）有三级降级链——原生 tool_calls、提示词计划、确定性脚本；断网用 `-Offline` 一键重启（本地 broker + Mock API）。**降级本身就是设计的一部分，我会当场说明。**

**Q13（刁钻）：你这个平台如果模型厂商自己做了工具市场，还有价值吗？**
> 有——因为问题不在"工具从哪来"，在"接进来以后谁保证安全"。工具越多、来源越杂，越需要一个与调用方解耦的安全管道和统一描述。模型厂商的生态越繁荣，中间这一层"统一描述 + 必经安全 + 硬件接入"的价值越大。USB-C 不是某一家手机厂的专利，恰恰是所有厂商共用的标准。
