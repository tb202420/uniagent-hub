下面把你的方案整理成一条可执行的研发路线。核心思路是：**先冻结规范，再打通垂直链路；先只读单工具，再多类型多工具；先 CLI 后 IoT/REST；安全从第一行代码开始横切；最后做编排、可视化和比赛演示。**

---

## 一、总体开发原则

1. **规范先行**：先定 `UniSpec v0.1`，所有模块都围绕它开发。
2. **垂直切片优先**：不要先写完整平台，而是先实现“Agent → MCP Gateway → CLI 适配器 → 真实命令”的最小闭环。
3. **先易后难**：CLI 适配器最简单，先做；MQTT 设备受硬件影响，先用 Python 模拟器；REST 最后接。
4. **安全内建**：参数校验、命令注入防护、权限、审计从 MVP 就加入，而不是后期补。
5. **演示驱动**：所有开发围绕最终 5 分钟演示场景收敛，避免功能发散。

---

## 二、开发阶段路线图

### 阶段 0：需求冻结与架构定稿（2–3 天）

**目标**：把方案变成可开发的接口契约。

**任务**：
- 明确比赛评分点：创新性、工程完整性、安全、演示效果。
- 冻结 `UniSpec v0.1`：定义 `id/type/name/protocol/endpoint/capabilities/constraints`。
- 定义 MCP Gateway 三个核心接口：`tools/list`、`tools/call`、`server/discover`。
- 定义适配器统一接口：`discover()`、`list_tools()`、`call_tool()`。
- 确定演示场景：建议“智能办公环境管理”：温度传感器 + 空调控制 + Git 状态 + 天气 API。
- 建代码仓库与任务看板。

**交付物**：
- PRD、架构图、UniSpec v0.1、接口文档、任务清单。
- Docker Compose 雏形。

**验收**：
- 所有模块接口不再频繁变动。
- 能画出完整数据流：Agent → Gateway → Adapter → 资源。

---

### 阶段 1：MVP 垂直链路（第 1–2 周）

**目标**：打通最小可用链路，验证核心主张。

**开发顺序**：
1. 实现 `UniSpec` Pydantic 模型与校验。
2. 实现内存版 `ToolRegistry`。
3. 实现 CLI 适配器：
   - 解析 YAML 注册配置。
   - 解析 `{placeholder}` 生成 JSON Schema。
   - 使用 `subprocess.run([...], shell=False)` 执行，禁止字符串拼接。
4. 实现最小 `MCP Gateway`：
   - `tools/list` 返回统一工具列表。
   - `tools/call` 路由到 CLI 适配器。
5. 实现 Agent Demo：
   - 用 MCP Client 调用 `git_status` 或 `file_search`。
6. 加入 MQTT 模拟设备：
   - Python 脚本模拟 ESP32 发布温度。
   - 实现 MQTT 适配器，注册 `get_temperature`。

**交付物**：
- 可运行 Demo：Agent 调用 1 个 CLI 工具 + 1 个 MQTT 设备工具。
- 调用日志与审计记录。

**验收**：
- Agent 不知道背后是 CLI 还是 MQTT，只通过 MCP 工具调用成功。
- 完整链路延迟可观测。

---

### 阶段 2：核心模块与多类型适配（第 3–5 周）

**目标**：实现“一规范多类型”，完成至少 5 个工具注册。

**任务**：
- 完善 `UniSpec`：支持 IoT、CLI、REST、本地脚本。
- 实现 `ToolRegistry` 持久化：SQLite 存储 UniSpec、权限、日志。
- 实现四类适配器：
  - MQTT 设备适配器：设备上线发布 UniSpec 到 `uniagent/register`，自动发现。
  - CLI 适配器：Schema 自动生成、沙箱执行、超时控制。
  - REST 适配器：导入 OpenAPI Spec，自动生成 MCP Tool。
  - 本地脚本适配器：Python/Shell 脚本注册与执行。
- 实现 Gateway 多工具路由与多服务器聚合。
- 实现 `server/discover`，支持协议版本协商。
- 实现 Guard v1：
  - 工具级权限：`readOnly/write/admin`。
  - 参数校验：基于 `inputSchema`。
  - 审计日志：`trace_id/tool_name/args/result/latency`。

**交付物**：
- 至少 5 个工具：2 个 IoT、2 个 CLI、1 个 REST。
- 统一 `tools/list` 输出。
- 权限与参数校验拦截记录。

**验收**：
- Agent 通过同一 MCP 接口调用所有类型工具。
- 恶意参数如 `; rm -rf` 被拦截。
- 审计日志可查询。

---

### 阶段 3：工作流编排与安全增强（第 6–7 周）

**目标**：从单工具调用升级为多工具编排。

**任务**：
- 实现 `WorkflowEngine`：
  - JSON 工作流蓝图。
  - 拓扑排序执行。
  - 支持依赖、并行、数据管道 `{{s1.output}}`。
  - 暴露 `run_workflow` 工具。
- 实现 Guard v2：
  - 速率限制：按工具 ID 与调用方。
  - 沙箱增强：文件系统白名单、CPU/内存限制。
  - 注入防护：参数白名单、类型强校验。
- 实现 CLI 反向生成：将 MCP 工具生成 CLI 脚本，方便调试。
- 加入可观测性：
  - `structlog` JSON 日志。
  - Prometheus 指标可选。
  - 简单 Web 审计界面。

**交付物**：
- 工作流示例：“查询温度 → 判断 > 28°C → 开空调”。
- 一次 `run_workflow` 调用完成多步任务。
- 安全测试报告。

**验收**：
- Agent 只消耗一次调用 token 完成多工具编排。
- 越权、超时、限流、注入均被正确拦截。

---

### 阶段 4：演示、文档与答辩（第 8 周）

**目标**：把技术成果转化为比赛可展示、可理解、可复现的交付物。

**任务**：
- 设计 5 分钟演示脚本：
  1. 展示工具注册中心：IoT、CLI、REST 工具统一列表。
  2. Agent 调用温度传感器。
  3. Agent 触发工作流：温度过高 → 开空调。
  4. 展示审计日志与安全拦截。
  5. 展示 CLI 反向生成。
- 准备备用方案：离线视频、MQTT 模拟器、本地 Ollama。
- 编写文档：
  - README、部署指南、UniSpec 规范、API 文档、测试报告。
- 制作 PPT 与答辩讲稿。
- 强调创新点：协议无关、UniSpec、安全内建、无状态网关、CLI 双向生成。

**交付物**：
- 可一键 Docker Compose 启动的系统。
- 演示视频、PPT、技术文档、测试报告。

**验收**：
- 现场演示稳定，断网/设备掉线有降级方案。
- 评委能听懂“AI 世界的 USB-C”这一核心比喻。

## 三、模块依赖与开发顺序

```
UniSpec v0.1
   ↓
ToolRegistry
   ↓
CLI 适配器 → MCP Gateway → Agent 联调
   ↓
MQTT 适配器 / REST 适配器 / 脚本适配器
   ↓
Guard 安全模块（横切）
   ↓
WorkflowEngine
   ↓
CLI 反向生成 + 可观测性 + 演示界面
```

**关键判断**：
- 不要先写工作流引擎，因为底层工具调用不稳定时，编排没有意义。
- 不要先接真实 ESP32，先用 MQTT 模拟器验证协议。
- 不要先做漂亮前端，先保证 `tools/list` 和 `tools/call` 稳定。

## 五、测试与验收重点

| 测试类型 | 内容 | 验收标准 |
|---|---|---|
| 单元测试 | UniSpec 校验、模板解析、参数校验 | 覆盖率 > 70% |
| 集成测试 | MQTT/CLI/REST → Gateway | 工具发现与调用成功 |
| 端到端 | Agent 调用工作流 | 多步任务一次完成 |
| 安全测试 | 命令注入、越权、超时、限流 | 全部拦截并记录 |
| 性能测试 | 工具调用延迟 | 单工具 < 500ms，参考 205ms |
| 演示测试 | 5 分钟脚本 | 连续 3 次无失败 |

## 六、主要风险与应对

| 风险 | 应对 |
|---|---|
| MCP 规范版本变动 | 以官方 SDK 为准，抽象传输层，先支持 stdio + HTTP |
| ESP32 硬件不稳定 | 先用 Python MQTT 模拟器，真实设备仅演示 |
| LLM 输出不稳定 | 演示时用固定 Agent 脚本 + 工具白名单 |
| 沙箱实现复杂 | 先做参数白名单 + `shell=False`，再逐步加资源限制 |
| 时间不足 | 优先保证 MVP + 核心模块，工作流与前端可降级 |
| 答辩讲不清 | 用“USB-C 接口”比喻，强调 UniSpec 统一抽象 |
