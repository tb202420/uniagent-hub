# 我的研究过程与试错记录（v3.0）

> 说明：以下失败都是开发中真实发生的，修正后的代码在仓库可查；日志片段来自
> `data/demo_runs/`、`data/pytest-v30.xml` 与当次调试输出。截图需在演示录屏时
> 补拍（涉及人工操作，本阶段不代拍）。

## 试错一：审批等待把事件循环堵死，前端永远看不到审批卡片

**现象**：第一版把 HITL 等待直接写在 `/mcp` 的 `async def` 路由里。`gateway.call()`
是同步函数，`approvals.wait()` 一阻塞就是 90 秒——这 90 秒里 uvicorn 的事件循环
被占满，`/ws/events` 推不出事件，`/hitl/decide` 也进不来。逻辑上"等待人工审批"，
实际上"人和前端都被挡在门外"，形成死锁。

**定位**：用 `websockets` 客户端连 `/ws/events`，审批前后一条事件都收不到；
`curl /hitl/pending` 也超时。确认不是审批 Broker 的问题，而是路由把同步阻塞放进了
事件循环。

**修正**：把 `tools/call` 改成 `await run_in_threadpool(gateway.call, ...)`，
让审批阻塞只占线程池的一个线程；事件循环继续服务 WS 与审批端点。代码注释里留了
硬约束说明（`core/gateway/server.py` 的 `call()` 文档串与 `/mcp` 路由）。

**结果**：`demo/irrigation_approval.py` 连续 10 次连跑，审批等待稳定在
2.97–3.03s，事件流实时可见（`data/demo_runs/run10_*.log`，10/10 通过）。

## 试错二：Windows 上没有 PTY，"终端接管"差点变成假功能

**现象**：按技术栈直接 `import pty`，在 Windows 上 ImportError；查 ConPTY 方案，
需要额外引入 `pywinpty`。如果为了"看起来像 PTY"而硬套一个一次性 `subprocess`，
终端里连 `cd` 都不保留状态，接管就是假的。

**取舍**：POSIX 保留 stdlib `pty` 伪终端；Windows 改为**持久 stdin/stdout 管道
会话**（`subprocess.Popen` + 读线程 + 写入锁），并如实标注"Windows 管道会话
（非 PTY）"。两种模式共用同一套字节流、输入 Guard、token 与接管状态机，前端
xterm.js 无感知。

**验证**：`tests/unit/test_terminal_session.py` 用当前解释器起"回显 stdin"的
持久子进程，在 Windows 走 pipe、在 POSIX 走 pty，两条路径都断言
`echo → ECHO:hello` 往返；`tests/integration/test_v30_gateway_api.py`
再走一遍真实 WebSocket 的 `echo ua_probe` 与 `curl` 拦截。

**反思**：与其写"全平台 PTY"，不如写清楚"哪里是 PTY、哪里是管道"。

## 试错三：审批粒度太细，演示会变成"点不完的确认框"

**现象**：最初的想法是"所有 write 工具都审批"。但演示链路里 `run_workflow`、
`ac_control`、`db_execute` 都是 write；一次工作流会连续弹多次审批，评委还没看到
硬件动作，先点了七八次"允许"。

**修正**：审批闸门只对 `HUB_APPROVAL_TOOLS`（默认 `control_pump`）生效，且只在
write/admin 权限下触发；只读工具继续自动放行。拒绝/超时复用 1003，不新增错误码，
保持 `docs/api.md` 的错误码冻结。审批决策（含超时）写入审计哈希链，
`tool=hitl.approval`，可用 `/api/audit/verify` 校验。

**结果**：演示中审批卡片只弹一次；`run_workflow` 只读步骤静默执行。
`tests/unit/test_hitl.py` 用 9 个用例锁住"只对 write 目标触发"和"只读跳过"。

## 试错四：前端包体 1.4MB，xterm 把首屏拖慢

**现象**：接入 `@xterm/xterm@6` 后 `npm run build` 报 chunk > 900kB；
xterm 与 React Flow 都被打进入口 chunk，低配机器首屏要等。

**修正**：xterm 改为在进入控制层时动态 `import()`（代码分割后
`xterm-*.js` 332kB 独立成块，首屏 `index-*.js` 降到 438kB）；
React Flow 保持编排层按需加载。构建警告保留但不再阻塞，CI 的 `spa-build` 通过。

**反思**：性能问题不一定要"上更复杂的框架"，先把不该进首屏的依赖挪走。

## 试错五：事件流里的 span 少了一条结束事件

**现象**：演示日志统计 `span.start=5`、`span.end=4`。最初怀疑 tracer 丢事件，
后来对照时间戳发现：`tool.run_workflow` 的 `span.end` 在审批人线程
`stop.set()` 之后才发出，采集端提前退出，属于**采集窗口**问题，不是 span 泄漏。

**修正**：演示脚本改为在 Agent 返回后再等待 0.3s 收尾，再停止采集；
同时在 `SpanWaterfall` 里对 `status=running` 的 span 显示为"进行中"，不把
"还没结束"误判成失败。

**反思**：证据链里的"少一条"要先分清是产品 bug 还是采集 bug，不能直接改数字。
